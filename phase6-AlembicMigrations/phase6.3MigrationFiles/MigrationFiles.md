# 1. What is a Migration File?

A migration file is a Python file generated by Alembic that contains the instructions required to update or revert the database schema.

It acts as a **record of a database schema change**.

Example:

```text
alembic/

└── versions/

    a1b2c3d4_add_email_to_students.py
```

Each migration file represents one change made to the database.

---

# 2. Structure of a Migration File

Example:

```python
"""Add email column

Revision ID: a1b2c3d4
Revises: z9y8x7w6
"""

from alembic import op
import sqlalchemy as sa

revision = "a1b2c3d4"
down_revision = "z9y8x7w6"

def upgrade():
    op.add_column(
        "students",
        sa.Column("email", sa.String(), nullable=True)
    )

def downgrade():
    op.drop_column("students", "email")
```

Important components:

- `revision`
- `down_revision`
- `upgrade()`
- `downgrade()`
- `op`

---

# 3. `revision`

Example:

```python
revision = "a1b2c3d4"
```

`revision` is the **unique identifier of the current migration**.

It is similar to a Git commit hash.

Every migration has its own unique revision ID.

Purpose:

- Uniquely identify each migration.
- Track migration history.
- Support upgrades and downgrades.
- Maintain the migration chain.

---

# 4. `down_revision`

Example:

```python
down_revision = "z9y8x7w6"
```

`down_revision` stores the **revision ID of the previous migration**.

It tells Alembic which migration comes before the current one.

Example:

```text
001_create_students

↓

002_add_email

↓

003_create_notes
```

Here:

```text
002.down_revision = 001

003.down_revision = 002
```

This creates a linked chain of migrations.

Without `down_revision`, Alembic would not know the correct order of migrations.

---

# 5. `upgrade()`

Example:

```python
def upgrade():
    op.add_column(...)
```

The `upgrade()` function contains the instructions required to move the database **forward** to a newer schema version.

Typical operations include:

- Create table
- Add column
- Create index
- Add foreign key
- Add constraints

It is executed when running:

```bash
alembic upgrade head
```

or upgrading to any newer revision.

---

# 6. `downgrade()`

Example:

```python
def downgrade():
    op.drop_column(...)
```

The `downgrade()` function contains the instructions required to move the database **backward** to a previous schema version.

Typical operations include:

- Drop table
- Remove column
- Remove index
- Remove foreign key

It is executed when running:

```bash
alembic downgrade <revision>
```

or any downgrade command.

# 7. What is `op`?

Example:

```python
from alembic import op
```

`op` stands for **Operations**.

It is Alembic's toolkit for modifying the database schema.

Instead of writing raw SQL statements, developers use the helper functions provided by `op`.

---

# 8. Common Alembic Operations

### Create Table


Creates a new database table.

### Drop Table

# 9. Migration Chain

Alembic stores migrations as a linked chain.

Example:

```text
001_create_students

↓

002_add_email

↓

003_create_notes

↓

004_add_phone
```

Each migration knows:

- Its own revision ID.
- The previous revision (`down_revision`).

This allows Alembic to determine:

- Migration order
- Current database version
- Upgrade path
- Downgrade path

---

# 10. Why Should Migration Files Never Be Deleted?

Suppose the project contains:

```text
001_create_students

↓

002_add_email

↓

003_create_notes
```

If:

```text
002_add_email
```

is deleted, the chain becomes:

```text
001_create_students

↓

???

↓

003_create_notes
```

Alembic can no longer determine how to reach the next migration.

Deleting migration files may result in:

- Broken migration history
- Upgrade failures
- Downgrade failures
- Version mismatch between team members

Therefore, migration files should always be kept under version control.

---

# 11. Example

Suppose the developer adds:

```python
phone = mapped_column(String)
```

Alembic generates:

```python
def upgrade():
    op.add_column(
        "students",
        sa.Column("phone", sa.String(), nullable=True)
    )

def downgrade():
    op.drop_column("students", "phone")
```

Applying:

```bash
alembic upgrade head
```

adds the column.

Downgrading removes it.

---

# 12. Best Practices

- Never delete migration files.
- Keep migration history under Git.
- Review migration files before applying them.
- Use descriptive migration messages.
- Let Alembic generate migrations whenever possible.
- Understand what `upgrade()` and `downgrade()` are doing before executing them.

# 14. Quick Cheat Sheet

| Feature | Purpose |
|----------|---------|
| Migration File | Stores database schema changes |
| `revision` | Unique ID of the current migration |
| `down_revision` | Revision ID of the previous migration |
| `upgrade()` | Move database to a newer schema version |
| `downgrade()` | Revert database to an older schema version |
| `op` | Alembic Operations toolkit |
| `op.create_table()` | Create a table |
| `op.drop_table()` | Delete a table |
| `op.add_column()` | Add a column |
| `op.drop_column()` | Remove a column |
| Migration Chain | Maintains migration order |

---

# 15. Key Takeaways

- A migration file records a single database schema change.
- Every migration has a unique **revision ID**.
- `down_revision` links each migration to the previous one, forming a migration chain.
- `upgrade()` contains instructions to move the database to a newer schema version.
- `downgrade()` contains instructions to revert the database to a previous schema version.
- `op` (Operations) provides helper functions for modifying the database schema without writing raw SQL.
- Common operations include creating tables, dropping tables, adding columns, removing columns, and managing indexes.
- Migration files should never be deleted because they preserve the complete history and order of schema changes.
- Understanding migration files helps developers safely evolve database schemas over time.
