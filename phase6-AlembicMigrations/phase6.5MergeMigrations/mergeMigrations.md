---

# 1. Working Alone vs Working in a Team

When working alone, migrations usually form a straight chain.

Example:

```text
001_create_students

↓

002_add_email

↓

003_create_notes

↓

004_add_phone
```

There is only one latest migration.

In a team, however, multiple developers may create migrations simultaneously.

Example:

```text
        003

       /   \

004_add_email    004_add_phone
```

Now there are two latest migrations.

These are called **multiple heads**.

---

# 2. What is a Migration Head?

A **head** is the latest migration in a migration chain.

Example:

```text
001

↓

002

↓

003
```

Here:

```text
003 = Head
```

If two developers create migrations from the same revision:

```text
        003

       /   \

004_A     004_B
```

Both become heads.

---

# 3. Why Do Multiple Heads Occur?

Multiple heads usually occur when:

- Two or more developers create migrations independently.
- Both migrations are based on the same previous revision.
- Both migrations are merged into Git without being merged in Alembic.

Even if the developers modify different tables, multiple heads can still occur because both migrations originate from the same parent revision.

---

# 4. Why Are Multiple Heads a Problem?

Alembic expects migrations to form a single linear chain.

Example:

```text
001

↓

002

↓

003

↓

004
```

With multiple heads:

```text
        003

       /   \

004_A     004_B
```

Alembic cannot determine which migration should be considered the latest.

This ambiguity prevents proper migration management until the heads are merged.

---

# 5. Viewing All Heads

Command:

```bash
alembic heads
```

Example Output:

```text
04a8f...

17bc2...
```

This command displays all current migration heads.

If more than one head is shown, a merge migration is usually required.

---

# 6. Merge Migrations

Alembic provides the `merge` command to combine multiple heads into a single migration.

Command:

```bash
alembic merge -m "Merge migrations" <head1> <head2>
```

Example:

```bash
alembic merge -m "Merge student and notes migrations" 04a8f 17bc2
```

Alembic generates a new merge migration.

Example:

```text
        003

       /   \

004_A     004_B

      \   /

      005_merge
```

The migration history becomes linear again.

---

# 7. Why Merge Migrations Are Useful

Merge migrations help:

- Resolve multiple migration heads.
- Restore a single migration chain.
- Keep migration history organized.
- Allow Alembic to continue upgrading and downgrading correctly.

---

# 8. Team Collaboration

Suppose:

Developer A creates:

```text
Add email column
```

Developer B creates:

```text
Create notes table
```

Both create migrations from revision `003`.

Result:

```text
        003

       /   \

004_email    004_notes
```

After pulling the latest code, one developer creates a merge migration:

```text
        003

       /   \

004_email    004_notes

      \     /

      005_merge
```

Now the project again has a single migration head.

---

# 9. Alembic Best Practices

## Generate migrations after pulling the latest code

Always pull the latest changes before creating a new migration.

This reduces the chances of multiple heads and merge conflicts.

---

## Commit migration files to Git

Migration files are part of the project and should always be committed.

Never ignore or exclude them from version control.

---

## Review autogenerated migrations

Alembic generates migration scripts automatically, but they may not always be correct.

Always inspect migration files before applying them.

---

## Use descriptive migration messages

Bad:

```text
update
```

Good:

```text
Add phone column to students
```

Descriptive messages make migration history easier to understand.

---

## Keep one logical change per migration

Good:

```text
Add email column
```

Bad:

```text
Add email

Rename user

Delete notes

Create payments
```

Each migration should represent one logical database change.

---

## Never delete migration files

Migration files preserve database history.

Deleting them can break the migration chain and prevent upgrades or downgrades.

---

# 10. Example Workflow

```text
Pull Latest Code

↓

Modify SQLAlchemy Models

↓

Generate Migration

↓

Review Migration

↓

Commit Migration

↓

```

If multiple heads occur:

```text
Detect Heads

↓

Create Merge Migration

↓

Commit Merge Migration

↓

Continue Development
```

# 12. Quick Cheat Sheet

| Command / Feature | Purpose |
|-------------------|---------|
| `head` | Latest migration in a chain |
| Multiple Heads | Two or more latest migrations |
| `alembic heads` | Show all current migration heads |
| `alembic merge -m "message" <head1> <head2>` | Merge multiple heads |
| Merge Migration | Combines multiple heads into one linear chain |
| Pull Latest Code | Reduces merge conflicts |
| Review Migrations | Prevents incorrect schema changes |

# 13. Key Takeaways

- A **head** is the latest migration in a migration chain.
- Multiple heads occur when different migrations are created from the same parent revision.
- Multiple heads can happen even if developers modify different tables.
- `alembic heads` displays all current migration heads.
- `alembic merge` creates a merge migration that combines multiple heads into a single linear history.
- Merge migrations allow Alembic to continue upgrading and downgrading databases correctly.
- Always pull the latest code before creating new migrations.
- Commit migration files to version control.
- Review autogenerated migrations before applying them.
- Keep migration messages descriptive and each migration focused on a single logical change.
