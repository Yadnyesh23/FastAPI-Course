# Phase 7.2 — JWT (JSON Web Token)

## What is JWT?

JWT (JSON Web Token) is a compact, URL-safe token used for **authentication** and securely transmitting information between the client and the server.

After a user logs in successfully, the server generates a JWT and sends it to the client. The client includes this token in every protected request, allowing the server to identify and authenticate the user.

---

# Why Do We Need JWT?

HTTP is a **stateless protocol**.

This means the server does **not** remember previous requests.

Example:

```
Request 1 (Login)
        │
        ▼
Server verifies user
        │
        ▼
Request Ends

--------------------------

Request 2 (Get Projects)

The server does NOT know who sent it.
```

Without JWT, the user would have to send their email and password with every request.

JWT solves this problem by allowing the client to send a signed authentication token instead.

---

# Authentication Flow

```
User Login
     │
     ▼
Verify Password
     │
     ▼
Generate JWT
     │
     ▼
Return JWT to Client
     │
     ▼
Client Stores JWT
     │
     ▼
Future Requests

Authorization: Bearer <JWT>
```

---

# JWT Structure

A JWT consists of **three parts** separated by dots (`.`).

```
HEADER.PAYLOAD.SIGNATURE
```

Example:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTYiLCJleHAiOjE3NzAwMDAwMDB9.
Wn2nSgR9B8KzY...
```

---

# Part 1 — Header

The header contains metadata about the token.

Example:

```json
{
    "alg": "HS256",
    "typ": "JWT"
}
```

### Common Fields

- `alg` → Algorithm used to sign the token
- `typ` → Token type (JWT)

---

# Part 2 — Payload

The payload contains information about the authenticated user.

Example:

```json
{
    "sub": "user_uuid",
    "email": "abc@gmail.com",
    "role": "admin"
}
```

The information stored inside the payload is called **Claims**.

---

# Common JWT Claims

## sub (Subject)

Usually stores the User ID.

```json
{
    "sub": "6fd2..."
}
```

---

## exp (Expiration Time)

Specifies when the token expires.

```json
{
    "exp": 1723567890
}
```

---

## iat (Issued At)

Specifies when the token was created.

```json
{
    "iat": 1723564290
}
```

---

## nbf (Not Before)

Token cannot be used before this time.

---

# Part 3 — Signature

The signature ensures that:

- The token was generated by your server.
- The payload has not been modified.

The signature is created using:

```
Header
+
Payload
+
Secret Key
        │
        ▼
Signature
```

If anyone changes the payload, the signature becomes invalid and the server rejects the token.

---

# Is JWT Encrypted?

**No.**

JWT is:

- Encoded
- Signed

It is **not encrypted**.

Anyone can decode:

- Header
- Payload

Therefore, never store sensitive information inside a JWT.

---

# Never Store These Inside JWT

- Password
- OTP
- Credit Card Details
- API Keys
- Sensitive Personal Information

JWT should contain only the information required for authentication and authorization.

---

# What is SECRET_KEY?

`SECRET_KEY` is a secret value known only to the server.

It is used to:

- Generate JWT signatures
- Verify JWT signatures

Example:

```
Header
+
Payload
+
SECRET_KEY
        │
        ▼
Generate Signature
```

Without the correct secret key, no one can generate a valid JWT.

---

# Where Should SECRET_KEY Be Stored?

Store it inside:

```
.env
```

Example:

```env
SECRET_KEY=your-super-secret-random-key
```

Never hardcode it inside your source code.

---

# Why Should SECRET_KEY Never Be Committed?

If someone gets your secret key, they can generate valid JWTs for any user.

Example:

```
{
    "sub": "attacker",
    "role": "admin"
}
```

The attacker can sign it using your secret key, and your server will trust it.

Treat `SECRET_KEY` like a database password.

---

# JWT Configuration

Inside `config.py`:

```python
SECRET_KEY: str

ALGORITHM: str = "HS256"

ACCESS_TOKEN_EXPIRE_MINUTES: int = 30
```

---

# Why Do Tokens Expire?

If a token never expires:

```
Token
    │
    ▼
Valid Forever ❌
```

If it is stolen, the attacker has permanent access.

Instead:

```
Token
    │
    ▼
Expires after 30 minutes
```

The user must authenticate again (or use a refresh token).

# JWT Utility Functions

## Create Access Token

```python
def create_access_token(data: dict):
```

Responsibilities:

- Copy payload
- Add `iat`
- Add `exp`
- Sign JWT
- Return encoded token

---

## Decode Access Token

```python
def decode_access_token(token: str):
```

Responsibilities:

- Verify signature
- Verify expiration
- Decode payload
- Return payload as a dictionary

---

# Why Does create_access_token() Accept a Dictionary?

Instead of:

```python
create_access_token(user)
```

we use:

```python
create_access_token(payload)
```

Example:

```python
payload = {
    "sub": str(user.id),
    "email": user.email,
    "role": user.role
}

token = create_access_token(payload)
```

### Advantages

- Decoupled from database models
- Reusable for any authentication scenario
- Follows the Single Responsibility Principle (SRP)

---

# Why Should create_access_token() Add exp Automatically?

Instead of making every caller remember:

```python
payload["exp"] = ...
```

`create_access_token()` automatically adds:

- `iat`
- `exp`

This prevents bugs and ensures every token has an expiration time.

---

# Why Does decode_access_token() Return a Dictionary?

JWT only contains **claims**, not a complete database object.

Decoded payload:

```python
{
    "sub": "...",
    "email": "...",
    "role": "user"
}
```

Then:

```python
user = repository.get_user_by_id(payload["sub"])
```

The **database remains the source of truth**, while JWT is used only for authentication.

# Best Practices

- Store `SECRET_KEY` in `.env`.
- Never expose `SECRET_KEY` publicly.
- Never store passwords or sensitive information inside JWT.
- Always set an expiration time (`exp`).
- Keep access tokens short-lived.
- Use standard JWT claims (`sub`, `exp`, `iat`, `nbf`) whenever possible.
- Keep JWT utilities independent of database models.
- Always verify both the signature and expiration before trusting a token.

---

# Key Takeaways

- JWT is used for stateless authentication.
- JWT contains three parts: Header, Payload, and Signature.
- The payload stores claims about the user.
- The signature protects the token from tampering.
- JWT is **signed**, not **encrypted**.
- Store only non-sensitive information inside JWT.
- `SECRET_KEY` must remain private and should be stored in `.env`.
- `create_access_token()` should automatically add expiration and issue time.
- `decode_access_token()` should return the decoded payload, not a database model.
- After decoding a JWT, always fetch the user from the database using the `sub` claim.
